### 关键发现（性能特征）
1. **不是卡死，是锯齿形写入**：日志出现「读目录 1.5s → 静默 ~100s → 一次性 flush 200 条」的循环。
   单看 docs 计数会误判为停滞。
2. **实测吞吐 ~90–105 条/分钟**（01:13:27→01:21:14 共 671 条 / 7.3 分钟），
   远低于早期 200 条/40s（~300/分钟）。随索引增大（1.36→1.57GB）INSERT 明显变慢。
3. **WAL 与 FTS5 是瓶颈**：WAL 在 12–44MB 波动，`Checkpoint()` 的 `wal_checkpoint(TRUNCATE)`
   一旦被并发读事务挡回 busy 就静默跳过（非致命），WAL 涨大后 FTS5 INSERT 退化。
   代码注释自述「71MB WAL 时 200 条/批耗时 30s」，实测最慢一批 07/14 花了 **5分10秒/200 条**。
4. 档案文档体积大：db 从 1355MB 涨到 1566MB，约 400KB/文档 → backfill 本质是 I/O 密集。

**改动**（`internal/index/index.go` + 新增 `internal/index/docpaths_test.go`）：
1. `doc_paths` 表从 `(path)` 扩展为 `(path, tags)`，tags 与 docs 在同一事务内同步维护

### ⭐ 01:45 根因定位：FTS5 UNINDEXED 列 WHERE → 每条全表扫描（backfill 慢的元凶）

**现象**：07/23 目录 258 文件 01:36:39 读完，01:44:57 才 `flushed 200` —— 单批 **8 分 18 秒**。

**实测证据**（只读连接，真实库 22,504 行）：
| 查询 | 耗时 |
|---|---|
| `SELECT COUNT(*) FROM docs WHERE path='__nonexistent__'`（FTS5，path UNINDEXED） | **2.15 s** |
| `SELECT COUNT(*) FROM doc_paths WHERE path='__nonexistent__'`（普通表） | 0.0003 s |

**根因**：FTS5 虚拟表对 UNINDEXED 列（`path`/`nas_path`/`type`/`time`）做 `WHERE` 无法用索引，
只能**全表扫描**。而 `BulkIndex()` 对**每一条**文档都先执行
`DELETE FROM docs WHERE path = ?`（`index.go:317`），`Index()` 同样（`index.go:266`）。
- 200 条 × 2.15 s = **430 s/批**，与实测 498 s 吻合 → 慢的不是 INSERT，是这次无意义的扫描。
- **代价随数据量线性恶化**：索引到 46k 时约 4.5 s/次 → 一批 15 分钟。
- 影响面不止 backfill：**每次剪贴板同步的 `Index()` 写入也白白烧掉 2+ 秒**。

**实测吞吐**：25 条/分钟（2.4 s/条），剩余 24,426 条 → **ETA ≈ 16 小时**（不可接受）。

**修复方案（未实施，待确认）**：用 FTS5 的 `rowid` 做删除，把 O(n) 扫描降为 O(log n)。
1. `doc_paths` 增加 `rowid INTEGER` 列，记录每篇文档在 FTS5 中的 rowid。
2. 迁移：**一次**全表扫 `SELECT rowid, path FROM docs`（约 2–5 s，只做一次）灌入映射；
   绝不能逐条 `WHERE path=?` 回填（那样是 22.5k × 2s = 12 小时）。
3. 写路径：删除改 `DELETE FROM docs WHERE rowid = ?`；插入后用 `last_insert_rowid()`
   取新 rowid 写回 `doc_paths`。
4. backfill 场景路径已知未索引（`indexedSet` 判定过），本可完全跳过 DELETE；用 rowid 删除兜底即可。
预计单批从 8 分钟降到 **5–10 秒**。

**口径修正**：此前日志里「约 400KB/文档」有误。实测 `AVG(LENGTH(content)) = 8,929 B`（最大 2.99MB），
22,504 篇正文合计仅 **192MB**；db 1.57GB 的膨胀来自 **FTS5 trigram 倒排索引（约 8.5 倍）**，
`docs_data` 27.9 万 blob / `docs_idx` 24.3 万行。

**旁证**：`docs_idx` 是 `WITHOUT ROWID PRIMARY KEY(segid, term)` 的 B-tree，24 万行随机插入 → 页分裂，
随索引增大 INSERT 本身也在变慢（07/19–22 约 2–3 分钟/批 → 07/23 更慢）。

## 第三轮：nas_path 也走索引（commit ab91bd5，已 push）

### 根因（与 path 同病，换个列）
`/api/history/{id}/full` → `GetByNasPath()` → `WHERE nas_path = ?`，nas_path 是 FTS5
**UNINDEXED** 列 → 全表扫。**扫描代价随命中位置线性增长**（46,846 行实测）：
首行命中 0.00s（`LIMIT 1` 早停）／中间 5.6s／末尾 **10.4s**／未命中 9.6s。
历史条目多落在表尾 → 最坏档，叠加 SSH 兜底后接口端到端 **17~29 秒**。

⚠️ 教训：测 FTS5 UNINDEXED 全表扫时**不能只测一行**——`LIMIT 1` 遇到靠前的匹配会
提前返回，测出 0.00s 的假象。必须分「首行/中间/末尾/未命中」四个位置各测一次。

### 改动
- `doc_paths` 扩为 `(path, nas_path, tags, fts_rowid)` + 建 `idx_doc_paths_nas` 索引。
- `GetByNasPath` 改经该索引取 rowid 再按 rowid 命中（两次 O(log n)）。
- 抽出 `getDocByRowid`，`GetByPath`/`GetByNasPath` 共用。
- `needDocPathSync` 增加 `nas_path=''` 残缺检测（一次扫描同时判 fts_rowid=0 与空 nas_path）
  → **回填被进程杀掉后下次启动能自动续上**（本轮真的遇到了：02:34:08 查还剩 3346 行没填，
  02:34:12 就补完并打了 `meta synced: 46846 rows`）。
- `nas_path` 为空时短路返回 `(nil,nil)`，不误命中。

### 实测
- 迁移一次性回填 46,846 行 **17.2s**，零残留；建索引 0.17s。

- 内容无回归：与索引存储**字符数** 5/5 完全一致（注意 SQLite `length()` 返回**字符数**，

- `/api/v1/tags` 首次 201ms 是冷启动，随后 **20~27ms**（聚合 SQL 本体只 0.011s / 15,476 行）。
