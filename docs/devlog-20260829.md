## 2. 七项优化（`d770799`）

1. **Web Server 超时**（`internal/web/server.go`）：裸 `http.Server` 加 ReadTimeout 15s / WriteTimeout 10min / IdleTimeout 120s / MaxHeaderBytes 1MB——慢连接不再占用 goroutine
2. **Stats 增量化**（`internal/history/store.go`）：Append 增量维护日计数，Stats() 不再全量扫描；Compact/TrimTo 重置
3. **`/api/status` O(1)**：新增 `Store.Count()`（ensureCount 缓存计数），handleStatus 不再触发文件扫描
4. **去重修复**（`cmd/knowly/main.go`）：删除 5 秒全局门闩 + `lastProcessedTime`（会导致快速连续复制被误丢），改为纯内容哈希去重
5. **高频 DEBUG 日志门控**：两个每次剪贴板事件都打印的 DEBUG 行改为 `KNOWLY_DEBUG` 环境变量开启，daemon.log 不再无限膨胀
6. **发布并发上限**（`internal/publisher/publisher.go`）：`publishSem`（8 信号量），AI 发布风暴不再打满出站带宽
7. **微信 URL keep-alive 隔离**（`internal/fetcher/fetcher.go`）：微信对复用连接返回异常，`isWeChatURL` 单独禁用 keep-alive

## 3. `/full` 本地索引直读（`c1a30ce`，当日最大收益）

**瓶颈定位**：历史查看慢不是 jsonl O(N)，而是 `/full` 每次都 SSH 到 NAS 反查全文。本地 `index.db` 里明明已有全文（FTS 索引时下载过）。

**修复**（`internal/web/handlers.go` + `internal/index/index.go`）：

- `index` 包新增 `GetByNasPath(nasPath)`（`WHERE nas_path = ? LIMIT 1`）
- `handleHistoryEntryFull` 先经接口断言 `s.indexer.(interface{ GetByNasPath ... })` 查本地索引，命中直接返回；未命中才 SSH 兜底
- `handleSearch` 同步理顺：索引存在但查询出错应报错而不是静默滑向 SSH grep

**实测**：2.9s → 0.12s（SQLite 迁移后进一步到 24–49ms，见迁移日志）。

**这个发现直接改写了 SQLite 迁移的优先级判断**：jsonl 的 O(N) 从「性能救命」降级为「架构还债」。

## 4. stopDaemon 孤儿漏杀（`b3b2cad`）

**事故链**（当天下午真实发生）：Web UI 触发更新 → 旧进程未被杀干净成为孤儿 → LaunchAgent `KeepAlive=true` 每 10s 拉起新实例 → 新实例撞 pidfile 报「另一个 Knowly 守护进程正在运行」退出 → 循环。

**修复**（`cmd/knowly/main.go` stopDaemon 重写）：

1. `launchctl unload` 之后**必须**处理 pidfile，不再提前 return
2. pidfile 陈旧/非法 → 清理
3. 存活 PID → SIGTERM，200ms 轮询等 ≤5s，超时 SIGKILL
4. 这样孤儿（不经 launchd 的进程）也会被收干净

部署时验证 `launchctl kickstart -k` 不可用于非 launchd 管理的进程（exit 113 "Could not find service"），统一走 `knowly stop` / `knowly start`。

## 5. start 自愈 LaunchAgent（`dde96c8`）

修 stopDaemon 时追根因：`daemonPlistPath()` 在 plist 文件不存在时返回空串，`start` 会**静默**滑向直接 re-exec 的孤儿进程——不受 launchd 看护、崩溃无人拉起，正是事故链的出生点。

**新的 start 启动阶梯**：

```
1. ensureDaemonPlist()  ← plist 缺失时按当前可执行文件自愈生成
2. launchctl load       ← 常规路径
3. launchctl bootstrap  ← 现代 API 兜底
4. PID 探活防双开       ← launchd 全失败但已有实例在跑 → 不重复启动
5. 孤儿回退（最后手段）  ← 加 Setsid 脱离终端 + 显式告警「无看护模式」
```

`ensureDaemonPlist` 生成的 plist 与 npm 安装模板**逐字节一致**（diff 验证），含 KeepAlive/RunAtLoad/日志路径。实测：移走 plist → start → 自动重建并经 LaunchAgent 拉起。从此守护闭环：崩溃自拉、stop 收干净、plist 自愈、防双开。
