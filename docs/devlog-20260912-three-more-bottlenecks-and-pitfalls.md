## 一、开局：一个被误读为「卡死」的锯齿

凌晨 01:11 接手监控，第一眼是坏消息：日志停在 **01:08:12**，`docs` 计数冻在 **20405** 整整五分钟没动。
按常识这叫死锁。

但把证据摊开看，结论完全相反。我在此前挂了一个每 30 秒采样一次 `docs` 计数、WAL 尺寸、最新目录的监视器，
样本连起来是这么个形状：

```
读目录（1.5s，SSH tar 批量）→ 静默 ~100s（事务提交前计数不变）→ 一次性 flush 200 条
```

它不是卡住，而是**锯齿形慢写**。01:13:22 那条 `flushed 200` 之前的静默长达 **5 分 10 秒**，
不是挂掉，是那批特别慢。而我在 01:13:26 补发的重触发被日志挡了回来：

```
Index backfill already running, skip
```

这不是报错，是 `backfillMu.TryLock()` 守卫在工作——**幂等安全，不会重复跑**。这一条后来反复出现，
每次都是守护脚本的假阳性，无害，但噪声。

这里要记第一个教训：**「计数不变」不等于「进程不动」。** 批量事务在提交前，外部连接读到的
是旧快照。判断是否停滞，要看日志 mtime、WAL 尺寸、进程 PID 的组合，不能只看一个计数。

同时把口径校准了一次。我上 NAS 直接数了一遍真实文件数，发现此前的估算有偏差：

| 目录 | NAS 实际 | 当时已索引 | 状态 |
|---|---|---|---|
| 2026/04 | 1,817 | 1,817 | 完成 |
| 2026/05 | 7,731 | 7,731 | 完成 |
| 2026/06 | 4,625 | 4,625 | 完成 |
| 2026/07 | 7,459 | 2,906 | 进行中 39% |
| 2026/08 | 6,960 | 506 | 排队 7% |
| 2026/09 | 3,803 | 3,692 | 基本完成 97% |
| uploads | **14,535** | 0 | 未开始 |
| **合计** | **46,930** | 21,277 (45%) | — |

`uploads` 实际是 14,535 不是 16,552；文档正文平均只有 **8,929 B**，不是我此前估的 400KB。
口径错了，ETA 就全错——按当时的实测速率 **~93 条/分钟**，剩余 25,653 条约 4.5 小时，
我之前说的 55 分钟过于乐观。

## 二、第一根因：FTS5 的 UNINDEXED 列上做 `WHERE`，等于全表扫

锯齿的周期为什么从早期的 ~40 秒涨到 5~8 分钟？先看现象：

```
01:36:39  backfill dir 2026/07/23: 258 files read in 1.8s (258 ok)
01:44:57  backfill 2026/07/23: flushed 200
```

**读只花 1.8 秒，flush 花了 8 分 18 秒。** 慢的不是网络，是写入。

昨天刚修过 WAL 黑洞，所以第一反应是「WAL 又涨回去了」。但这次证据不支持这个猜测：采样显示
WAL 稳定在 **12–44MB**，没有失控迹象；而且 `flushed` 之间是**完全静默**的，不像 I/O 抖动
那种忽快忽慢。于是换掉「猜」的做法——直接在只读连接上量那两个可疑查询：

| 查询 | 耗时 |
|---|---|
| `SELECT COUNT(*) FROM docs WHERE path='__nonexistent__'`（FTS5，`path` 是 UNINDEXED） | **2.15 s** |
| `SELECT COUNT(*) FROM doc_paths WHERE path='__nonexistent__'`（普通表） | **0.0003 s** |

差了四个数量级。真相是：**FTS5 虚拟表对 `UNINDEXED` 列（`path` / `nas_path` / `type` / `time`）
做 `WHERE`，用不了任何索引，只能全表扫描。** 而 `BulkIndex()` 对**每一条**文档，写入前都先做一次
幂等前置删除：

```go
// 每条文档都执行一次
DELETE FROM docs WHERE path = ?
```

200 条 × 2.15 s = **430 秒/批**，与实测的 498 秒几乎完全吻合。**慢的不是 INSERT，是这次毫无意义的扫描。**

更糟的是它会随数据量**线性恶化**：索引到 46k 时约 4.5 s/次，一批要 15 分钟。
按当时 25 条/分钟算，剩余 24,426 条 → **ETA 约 16 小时**。而且它不只影响 backfill——
**每次剪贴板同步的 `Index()` 写入也白白烧掉 2 秒以上**，`GetByPath()`（详情接口）同病。

### 药方：用 `rowid` 把 O(n) 降成 O(log n)

FTS5 内部的 `rowid` 是有索引的。所以：

1. `doc_paths` 从 `(path)` 扩成 `(path, tags, fts_rowid)`——`fts_rowid` 记录每篇文档在 `docs` 里的行号；
2. 删除改 `DELETE FROM docs WHERE rowid = ?`；
3. 插入后用 `last_insert_rowid()` 取新 rowid 回写映射；
4. **迁移只能做一次全表扫** `SELECT rowid, path, tags FROM docs` 灌映射；
   绝不允许「逐条 `WHERE path=?` 回填」——那是 46k × 2s ≈ 26 小时。

顺手把 `tags` 也一起冗余进来：`status` / `tags` 这类聚合接口此前打的是 FTS5 的
`count(*)`，实测 **2.75 秒**（写入争抢时劣化到 7.6 秒），改查这张紧凑普通表只要 **0.027 秒**。

### 压测（真实数据快照，22,912 行）

上线前我照例用 SQLite 自己的 backup API 拷了一份快照（`cp` 对 WAL 库不安全），在上面先跑：

| 场景 | 耗时 |
|---|---|
| 旧：`DELETE WHERE path=?`（FTS5 全表扫） | **4,354 ms/条** → 200 条约 **871 秒** |
| 新：`DELETE WHERE rowid=?` | **0.035 ms/条** |
| 完整幂等重写 200 条（查 rowid → 按 rowid 删 → 插 → 回写） | **0.47 秒** |
| 迁移：一次全表扫回填 22,912 行 | 7.12 秒 |

单批 **871 秒 → 0.47 秒，约 1869 倍**，迁移一次性 7 秒。确认规模安全后才动线上。

上线后线上吞吐 **25 条/分钟 → 4,000+ 条/分钟**，`/api/v1/status` 从 2.75 s 掉到 **1.5 ms**，
`/api/v1/tags` 从 1.92 s 掉到 **20 ms**。

commit `c2bbcd7`。

## 三、第二根因：`ListDir` 把文件名里的连续空格折叠了

提速之后进度飞快，07 月到 08 月一口气吞掉。然后它走到 `uploads` 就停了——**索引数三分钟保持 0**，
日志里每 400 个文件报一次：

```
[WARN] backfill batch chunk failed at uploads (400 files): Process exited with status 2
```

`tar` 退出码 2 是致命错误。我上 NAS 手动复现：单文件 tar 正常，400 个也正常。那问题就不在 tar。

继续往下查，摸到了文件名。NAS 上有 **186 个** uploads 文件名含**连续空格**，例如：

```
st-dsv4_context_____-- 知识框架 --__    _knowledge_base.md
```

再回头看 `ListDir` 的实现，问题一目了然：

```go
fields := strings.Fields(line)          // 按空白切分
name := strings.Join(fields[7:], " ")   // 再用单个空格拼回去
```

`strings.Fields` 切分时会把**任意长度的连续空白**当一个分隔符，`Join` 再用**单个空格**拼回——
于是 `A    B` 被还原成 `A B`，一个 NAS 上根本不存在的路径。`tar` 找不到文件 → 退出码 2 →
整块 400 个文件全废。**更隐蔽的是降级路径**：逐文件读用的还是同一个错名字，也读不到。
这意味着**这 186 个文件本来永远无法入库**，而且不报错、不告警，只是安静地少了一批。

修复方式是把「切分再拼回」改成「**前缀定界后原样截取**」：前 7 列（权限、链接数、属主、属组、
大小、日期、时间）按空白切分，第 7 列之后的**整行剩余部分原样作为文件名**。抽成 `parseLsLine()`
以便单测，锁死这个行为（`internal/ssh/lsline_test.go`）。

### 顺带修掉的分块缺陷

排查时还发现 `readDirContents` 只按**文件数**分块（400 个）。归档月份目录单文件约 9KB，
400 个才 3.6MB，没问题；但 **uploads 单文件平均约 900KB**，400 个 tar 出来是 **367MB**——
`session.Output` 会在内存里留整块，解包成 map 再翻一倍，峰值 700MB+。

改成同时按**累计体积**封顶（`batchChunkBytes = 64MB`），大文件目录自动切小块。

commit `02bc050`。

## 四、第三根因：`nas_path` 同病——历史全文接口 20 秒

backfill 跑完后我对了一次账，几乎完美：NAS 上 46,933 个 `.md/.txt`，已索引 **46,846**，
缺失 87（86 条是 macOS 往非 HFS 卷拷贝时产生的 `._*` AppleDouble 资源叉垃圾，跳过才是对的；
剩 1 条是 backfill 走过该目录**之后**才生成的文件，属正常时间差）。索引侧脏数据 **0**。

### 附：怎么确认「一条都没漏」

对账的方法很朴素，但很有效——不要在索引侧自问自答，要**从数据源反向核**。
在 NAS 上 `find` 出全部 `.md/.txt` 的**相对路径**拉到本地（`sed 's|^\./||'` 去掉 `./`、`sort`），
再和索引里的 `path` 集合做双向差集：

```python
idx = set(r[0] for r in db.execute('SELECT path FROM doc_paths'))
nas = set(l.rstrip('\n') for l in open('/tmp/nas_paths.txt') if l.strip())
print('NAS 有索引无：', len(nas - idx))
print('索引有 NAS 无：', len(idx - nas))     # ← 这一项决定有没有脏数据
```

结果 `NAS 46,933 / 已索引 46,846 / 缺失 87 / 多余 0`。

**「多余 = 0」这一项比「已索引多少」更重要。** 它说明没有脏数据，也说明按 rowid 重写之后
**没有留下重复行或旧版本**——这正是本次改动最容易出问题的地方（rowid 映射一旦错位，
表现就是「条数看着正常，但内容张冠李戴」）。只看总数，是发现不了这种错的。

带着这份干净的数据，我去量了一遍控制台的真实接口耗时，捞到一个大问题：

| 接口 | 耗时 |
|---|---|
| `/api/status` | 1–4 ms |
| `/api/history?limit=20` | 3–12 ms |
| `/api/tags` | 0.9–2.5 ms |
| `/api/stats` | 12–79 ms |
| `/api/history/{id}` | 1.5–88 ms |
| **`/api/history/{id}/full`** | **20–29 秒** ⚠️ |

`/api/history/{id}/full` 就是控制台里**点开一条历史看全文**。它走 `GetByNasPath()`，
而 `nas_path` 又是 FTS5 的 UNINDEXED 列——**和中招的 `path` 是同一个病，换了个列**。

### 测全表扫不能只测一行（今天最值钱的一个教训）

第一次测，我拿 `SELECT ... WHERE nas_path = ? LIMIT 1` 随手取了一行，结果是 **0.00s**。
差点得出「没有性能问题」的结论。

`LIMIT 1` 会在遇到第一个匹配时就返回。查表头附近的行走运了，代价接近零；查表尾的行则要扫完整个表。
所以我把四个位置各测一次：

| 命中位置 | 耗时 |
|---|---|
| 首行 | 0.00 s（`LIMIT 1` 早停） |
| 中间 | 5.6 s |
| **末尾** | **10.4 s** |
| 未命中 | 9.6 s |

控制台的历史条目大多落在**表尾**，正好是最坏档——10 秒打底，叠加 SSH 兜底后接口端到端 **17~29 秒**。

**教训：测 UNINDEXED 列的全表扫，必须分「首行 / 中间 / 末尾 / 未命中」四点测，绝不只测一行。**

### 改动与实测

修法完全复用第一根因的套路：`doc_paths` 扩成 `(path, nas_path, tags, fts_rowid)` 并建
`idx_doc_paths_nas` 索引；`GetByNasPath` 改经索引取 rowid、再按 rowid 命中（两次 O(log n)）；
抽出 `getDocByRowid` 给 `GetByPath` / `GetByNasPath` 共用，去掉重复的取正文代码。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 单次查询（表尾命中） | 10.36 s | **0.002 ms** |
| 迁移一次性回填 46,846 行 | — | 17.2 s（零残留） |
| 线上 `/api/history/{id}/full` | 17~29 s | **0.9~47 ms** |

内容无回归：抽查 5 条，接口返回与索引存储**字符数 5/5 完全一致**。

commit `ab91bd5`（已 push，`7c70f7a..ab91bd5`）。

## 五、上线流程：预演、原子替换、验证

这一天我改了三次线上，线上一次都没翻车。靠的是一套固定的四步流程——值得固化下来。

### 第 1 步：改代码之前，先确认工作树里没有夹带

`git status` 报告有 **10 个未提交文件**时，千万别直接 `go build`。因为 `go build ./...`
编的是**整个工作树**，而不是你以为的那一个文件——你部署出去的二进制可能带着别人的半成品。

用 `git diff -w` 过滤掉空白差异后确认：8 个文件是纯 gofmt 空白/对齐重排，2 个只删了多余空行，
真正的逻辑改动只有自己的 `index.go`。结论：**部署的二进制 = HEAD + 格式重排 + 本次改动，无夹带。**

这个动作每次只要一分钟，但它决定了「出问题时该怀疑谁」。

### 第 2 步：在真实数据的只读副本上预演

改表（`ALTER TABLE` + 全表回填）是本项目风险最高的操作——索引库 **2.2GB**，改坏了就得重建。
这里有个坑：**`cp` 一个 WAL 模式的库是不安全的**，会拷到不一致的中间态。必须用 SQLite 自己的备份 API：

```python
src = sqlite3.connect('file:/Users/ygs/.knowly/index.db?mode=ro', uri=True)
dst = sqlite3.connect('/tmp/snap.db')
src.backup(dst)          # 得到一致性快照
```

在快照上先跑一遍 `ALTER` + 回填 + 压测，量出耗时和结果，确认规模可接受，再动线上。
今天的三次迁移都是这么过的：**6.96 s / 7.12 s / 17.2 s**，全部先预演。

### 第 3 步：原子替换 + kickstart

```bash
cd /Users/ygs/ygs/knowly
go build -ldflags "-X github.com/yuanguangshan/knowly/internal/web.BuildTime=\
$(date -u +%Y%m%d%H%M%S) -s -w" -o bin/knowly-darwin-arm64 ./cmd/knowly

TARGET=/opt/homebrew/lib/node_modules/knowly/bin/knowly-darwin-arm64
cp "$TARGET" "$TARGET.bak.$(date +%s)"       # 留一个回滚点
cp bin/knowly-darwin-arm64 "$TARGET.new"     # 先落到同目录临时名
mv -f "$TARGET.new" "$TARGET"                # 同目录 rename，原子生效
shasum -a 256 bin/knowly-darwin-arm64 "$TARGET"   # 校验落地一致

launchctl kickstart -k gui/$(id -u)/com.knowly.daemon
```

### 第 4 步：验证三件事

1. **启动日志里有没有预期的迁移行**——比如 `doc_paths meta synced: 46846 rows`。
   如果没有，说明迁移没跑或被跳过，此时**不要**继续后面的验证，先查原因。
2. **schema 与残留检查**——`PRAGMA table_info(doc_paths)` 是否已是新结构；
   `fts_rowid = 0` 和空 `nas_path` 是否为零。这两个是「映射残缺」的直接指标。
3. **重新触发 backfill**（重启会丢 goroutine），再实测接口延迟做前后对比。

顺带说一句：这三次里有一次我误判了。02:34:08 查库时还有 **3346 行** `nas_path` 没填，
看着像迁移失败；结果 **02:34:12** 它就自己补完并打了日志——我只是**看早了**。
**长任务要等它自己说完成，不要在跑到一半时下结论。**

## 六、踩坑清单：今天最值钱的部分

代码改动其实不大，真正花时间的是这些坑。逐条记下，避免下次再踩。

### 1. `LIMIT 1` 的早停会伪造出「很快」的假象

见上文。一个查询的真实代价取决于**匹配位置**，测试数据必须覆盖最坏档，否则测出的数字毫无意义。

### 2. SQLite `length()` 返回的是字符数，不是字节数

做内容一致性校验时，我拿 SQLite 的 `length(content)`（**字符数**）去比接口返回的 UTF-8 **字节数**，
中文一个字 3 字节，于是 6103 vs 10308，看着像内容被截断了，差点误判成回归。
改成同一口径（两边都取字符数或都取字节）后 **5/5 完全一致**。
**跨语言/跨层对比长度时，先确认单位。**

### 3. 长迁移必须可续跑——因为进程随时会被杀

我给 `needDocPathSync` 加了一条「残缺检测」：只要 `doc_paths` 里存在 `fts_rowid = 0` 或
`nas_path` 为空的行，下次启动就重新回填。加它的时候只是想「防御性编程」，**结果当天就用上了**：

```
02:34:08  （我查看）nas_path 还有 3346 行没填 —— 看着像失败
02:34:12  meta synced: 46846 rows     —— 它自己补完了
```

中途进程被杀过一次，重启后自动接上补完。如果当时写成「只回填一次、失败也不重试」，这 3346 行
就会永远缺着，而且**表里读不到任何异常**。凡是要扫全表的长迁移，触发条件就应该是
「数据是否完整」而不是「是否第一次运行」——幂等 + 可续跑。

### 4. `trash` 是同卷移动，空间不会立刻释放

清理 817MB 的旧索引备份 + 3 个旧二进制（共约 865MB）时，我用了 `/usr/bin/trash`
（Apple 自带的官方工具，进 Finder 废纸篓，可「放回原处」，比 `rm` 安全得多）。移完之后
`df` 一看——**还是 89%，一点没降**。因为同卷的 trash 只是移动文件位置，只有**清空废纸篓**才真正回收。
要清空间，得明确知道这一步还没发生。

### 5. zsh 不做单词分割（和 bash 不一样）

`for id in $IDS` 在 bash 里按空白拆成多个词，在 zsh 里 `$IDS` 会被当成**一个**词——
循环只跑一次、参数带上整串换行。测接口时因此得到一堆莫名其妙的空结果。
要么用 `while IFS= read -r`，要么显式 `setopt shwordsplit`。

### 6. 进程被周期性杀掉，比慢写更致命

`launchctl print` 显示 `last exit reason = OS_REASON_CODESIGNING`，且 `knowly.log` 里启动记录
多达 **98 次**，其中 **23:29:56–23:31:41 的 90 秒内重启了 10 次**。对 backfill 这种进程内
goroutine 来说，**只要进程还在被周期性杀掉，它就永远跑不完**——这个问题的优先级高于任何性能优化。

主要嫌疑是「原地覆盖二进制导致签名失效被 AMFI 杀」，因此部署改成了原子替换（做法见第五节）。
还有个必须记住的副作用：**重启会丢掉 backfill goroutine**（索引非空时不会自动重启），
所以每次部署后都要重新 `POST /api/v1/admin/backfill`——幂等安全，重触发只会 skip 已完成的目录。

### 7. 诊断工具本身会变成干扰源

「护栏脚本假阳性」是今天反复出现的噪声：`/tmp/bf_daemon.sh` 以「docs 三分钟不变」判定停滞，
可正常的 flush 周期本身就有 2~2.5 分钟静默，于是它周期性误触发。幸好 `backfillMu` 守卫挡住了，
只产生日志噪声、无实际危害。判断停滞应该看**日志 mtime**，而不是计数。

同样的教训昨天也吃过——一条远端 `grep` 在工具中断后继续跑了 1 小时 22 分，把 NAS IO 打满。
**诊断脚本必须有明确的生命周期管理。**

## 八、可复用的经验

1. **FTS5 的 UNINDEXED 列不能 `WHERE`。** 这是昨天第 3 层的延续——昨天发现了它「静默返回空」，
   今天发现了它的兄弟症状「能返回、但退化成 O(n) 全表扫」。**同一个坑，两种表情。**
   凡是要按某列精确查找，就把该列放进普通表并建索引，用 rowid 回指 FTS5。
2. **性能测试要测最坏档。** `LIMIT 1` 的早停、缓存命中、表头命中，都会把真实代价藏起来。
   分布式的答案（首行/中间/末尾/未命中）比一个平均值有用得多。
3. **长迁移的触发条件是「数据完整性」，不是「第几次运行」。** 幂等 + 可续跑，
   是应对「进程随时可能被杀」的唯一办法。
4. **跨层比较长度前先确认单位。** 字符数 ≠ 字节数，中文差 3 倍。
5. **部署要原子、要预演。** 覆盖运行中的二进制用同目录 `mv`；改表前用 SQLite 的
   `backup()` 在只读快照上演练迁移和压测（`cp` 对 WAL 库不安全）。
6. **警惕自己的工具。** 判断停滞看日志 mtime 不看计数；诊断脚本要有超时和清理；
   「工具中断」不等于「远端进程结束」。
7. **口径错了，一切推论都错。** 今天至少修正了两个口径：`uploads` 是 14,535 不是 16,552；
   正文平均 8,929 B 不是 400KB。**先量基线，再算 ETA。**
